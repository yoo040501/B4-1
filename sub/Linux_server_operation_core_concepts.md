# Linux 서버 운영 핵심 개념 정리

## 1. SSH 포트 변경 + Root 원격 접속 차단

- 기본 SSH 포트인 22번은 자동 스캔과 무차별 대입 공격의 대상이 되기 쉽다.
- 포트를 20022처럼 변경하면 자동화된 단순 스캔을 일부 줄일 수 있다.
- 다만 포트 변경만으로 강한 보안이 되는 것은 아니고, 핵심은 Root 원격 로그인을 막는 것이다.
- Root는 시스템 전체 권한을 가진 계정이므로 원격에서 직접 로그인하게 두면 계정 탈취 시 피해가 매우 크다.
- 그래서 일반 계정으로 로그인한 뒤 필요한 작업만 `sudo`로 수행하는 방식이 더 안전하다.

---

## 2. UFW에서 필요한 포트만 허용하는 이유

- 서버는 외부에서 접근할 필요가 있는 서비스만 열어두는 것이 기본 원칙이다.
- 이번 과제에서는 SSH용 `20022`, 앱용 `15034`만 허용했다.
- 그 외 포트는 기본적으로 차단해서 불필요한 공격 경로를 줄인다.
- 검증은 `sudo ufw status`로 실제 허용 규칙과 활성 상태를 확인한다.

---

## 3. 계정/그룹과 ACL로 공유/보안 디렉토리를 나누는 이유

- 모든 사용자에게 모든 파일 권한을 주면 실수나 계정 탈취 시 피해 범위가 커진다.
- 그래서 역할에 따라 권한을 나누는 최소 권한 원칙을 적용한다.
- `upload_files`는 admin/dev/test가 같이 써야 하므로 `agent-common` 그룹에 권한을 준다.
- `api_keys`, 로그 디렉토리는 민감한 정보가 있으므로 `agent-core`의 admin/dev만 접근하게 했다.
- ACL은 기본 Unix 권한보다 더 세밀하게 특정 사용자/그룹 권한을 지정하거나, 새 파일에도 기본 권한을 상속시키기 위해 사용한다.

---

## 4. 환경 변수로 실행 환경을 고정하는 이유

- 경로, 포트, 로그 위치 같은 값을 코드에 직접 박아두면 환경이 바뀔 때 코드를 수정해야 한다.
- 환경 변수를 사용하면 같은 프로그램을 개발/테스트/운영 환경에서 값만 바꿔 실행할 수 있다.
- 예를 들어 `AGENT_PORT=15034`, `AGENT_LOG_DIR=/var/log/agent-app`처럼 실행 조건을 외부에서 지정한다.
- 검증은 `env | grep '^AGENT_'` 또는 `echo $AGENT_HOME` 등으로 확인한다.

---

## 5. 쉘 스크립트로 상태를 수집하고 로그를 남기는 이유

- 장애가 발생했을 때 현재 상태만 보면 원인을 찾기 어렵다.
- 그래서 `pgrep`으로 프로세스, `ss`로 포트, `top`, `free`, `df`로 CPU·메모리·디스크 상태를 주기적으로 수집한다.
- 수집 결과를 `monitor.log`에 시간과 함께 남기면 장애 시점의 상태를 추적할 수 있다.
- 또한 임계값을 넘으면 `[WARNING]`을 출력해 이상 징후를 빠르게 확인할 수 있다.

---

## 6. crontab으로 주기 실행하는 이유

- 사람이 직접 `monitor.sh`를 실행하면 빠뜨릴 수 있고, 지속적인 관제가 어렵다.
- crontab에 매분 등록하면 시스템이 자동으로 반복 실행한다.
- 그래서 일정한 주기로 로그가 쌓이고, 장애 전후의 상태를 연속적으로 확인할 수 있다.

예:

```cron
* * * * * /home/agent-admin/agent-app/bin/monitor.sh >/dev/null 2>&1
```

---

## 7. 로그 압축/삭제 정책이 필요한 이유

- 로그를 계속 쌓기만 하면 언젠가 디스크가 가득 찬다.
- 디스크가 가득 차면 앱 로그 기록 실패, 서비스 장애, 시스템 문제로 이어질 수 있다.
- 그래서 `logrotate`를 사용해 로그가 일정 크기 이상 커지면 이전 로그를 회전시키고, 오래된 로그는 압축하고, 일정 개수만 보관한다.
- 이번 과제에서는 `10MB / 10개 / gzip 압축` 정책을 사용했다.

예:

```text
monitor.log
monitor.log.1.gz
monitor.log.2.gz
...
```

---

## 요약

이번 과제에서는 SSH와 UFW를 통해 외부 접근을 제한하고, 계정/그룹/ACL을 이용해 역할별 최소 권한을 적용하였다.

또한 환경 변수로 실행 환경을 분리하고, `monitor.sh`로 프로세스·포트·리소스 상태를 수집하여 로그로 남겼다. 이후 `crontab`으로 모니터링을 자동화하고 `logrotate`로 로그 용량을 관리하여 지속적인 서버 운영과 장애 추적이 가능하도록 구성하였다.


# 추가 운영 및 보안 고려사항

## 1. 브루트포스 공격 대응

SSH 포트를 기본 22번에서 20022번으로 변경하고 Root 원격 로그인을 차단하였지만, 포트 변경만으로 브루트포스 공격을 완전히 방지할 수는 없다.

브루트포스 공격은 동일한 계정에 대해 반복적으로 비밀번호를 시도하는 방식이므로 실제 운영 환경에서는 로그인 실패 횟수를 모니터링하고 반복적인 인증 실패가 발생하는 IP를 일정 시간 차단하는 추가 정책이 필요하다.

대표적인 대응 방법으로 `fail2ban`을 사용할 수 있다.

```bash
sudo apt install fail2ban
```

fail2ban은 SSH 인증 로그를 감시하고 일정 횟수 이상 로그인에 실패한 IP를 자동으로 차단할 수 있다.

추가적으로 다음과 같은 정책을 적용할 수 있다.

* SSH Key 기반 인증 사용
* 비밀번호 로그인 비활성화
* 로그인 실패 횟수 모니터링
* 특정 IP에서만 SSH 접근 허용
* fail2ban 등을 이용한 반복 공격 IP 자동 차단

따라서 이번 과제에서는 SSH 포트 변경과 Root 로그인 차단을 기본 보안으로 적용했으며, 실제 운영 환경에서는 fail2ban이나 SSH Key 인증을 추가하여 브루트포스 공격에 대응할 수 있다.

## 2. 다른 웹서버 또는 애플리케이션으로 전환할 경우

현재 `monitor.sh`는 다음 애플리케이션을 기준으로 작성하였다.

```text
Process : agent-app-linux-x86
Port    : 15034
Log     : /var/log/agent-app/monitor.log
```

향후 nginx, Apache 또는 다른 웹 애플리케이션으로 변경할 경우 다음 항목을 함께 변경하고 검증해야 한다.

### 체크리스트

1. 프로세스 이름

```bash
pgrep -f "nginx"
```

2. 서비스 포트

예를 들어 HTTP 서비스라면:

```bash
ss -ltn | grep ':80 '
```

HTTPS라면:

```bash
ss -ltn | grep ':443 '
```

3. 방화벽 정책

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
```

사용하지 않는 기존 포트는 제거한다.

4. 로그 파일 위치

서비스별 로그 위치에 맞게 변경한다.

예:

```text
nginx  : /var/log/nginx/
Apache : /var/log/apache2/
```

5. 모니터링 임계값

서비스의 특성에 따라 CPU, 메모리, 디스크 임계값을 조정한다.

따라서 애플리케이션이 변경될 경우 단순히 프로세스 이름만 변경하는 것이 아니라 **프로세스, 포트, 방화벽, 로그 경로, 임계값을 함께 확인해야 한다.**

---

## 3. 프로세스는 실행 중이지만 포트가 열리지 않는 경우

`monitor.sh`에서는 프로세스와 포트를 별도로 검사한다.

```text
Process Check : pgrep
Port Check    : ss
```

프로세스가 존재하더라도 포트가 LISTEN 상태가 아닐 수 있다.

이 경우 애플리케이션 실행 자체는 성공했지만 네트워크 포트 바인딩에 실패했을 가능성이 있다.

대표적인 원인은 다음과 같다.

### 1. 포트가 이미 사용 중인 경우

```bash
sudo ss -ltnp | grep 15034
```

다른 프로세스가 이미 15034 포트를 사용하고 있으면 애플리케이션이 해당 포트에 바인딩할 수 없다.

### 2. 잘못된 IP 또는 포트로 바인딩한 경우

애플리케이션이 예상한 `0.0.0.0:15034`가 아닌 다른 주소나 포트에서 실행될 수 있다.

```bash
sudo ss -ltnp
```

를 통해 실제 LISTEN 주소를 확인한다.

### 3. 권한 문제

일반적으로 1024 미만의 Well-known Port를 일반 계정이 직접 사용하려 하면 권한 문제가 발생할 수 있다.

### 4. 보안 정책 문제

SELinux 또는 AppArmor 같은 보안 정책이 활성화된 환경에서는 해당 정책에 의해 네트워크 바인딩이 제한될 수도 있다.

따라서 다음과 같은 상태:

```text
Process : [OK]
Port    : [FAIL]
```

가 발생하면 프로세스는 살아 있지만 서비스가 실제 요청을 받을 수 없는 상태로 판단한다.

이 경우 포트 사용 여부, 애플리케이션 로그, 바인딩 주소 및 보안 정책을 순서대로 확인한다.

## 4. 로그 급증 시 대응 정책

현재 `monitor.log`에는 다음 logrotate 정책을 적용하였다.

```text
size   10M
rotate 10
compress
```

일반적인 상황에서는 10MB 단위로 로그를 회전시키고 최대 10개의 과거 로그를 압축 보관한다.

하지만 장애나 반복 오류로 인해 로그가 매우 빠르게 증가하는 경우에는 logrotate만 기다리기보다 단계적으로 대응할 필요가 있다.

### 단기 대응

먼저 디스크 사용량과 로그 크기를 확인한다.

```bash
df -h
sudo du -sh /var/log/agent-app/*
```

디스크 부족으로 서비스 장애가 발생할 위험이 있는 긴급 상황에서는 불필요한 오래된 압축 로그부터 삭제할 수 있다.

예:

```bash
sudo rm /var/log/agent-app/monitor.log.10.gz
```

현재 사용 중인 `monitor.log`를 바로 삭제하는 것은 실행 중인 프로세스와 파일 디스크립터 문제를 만들 수 있으므로 우선 오래된 로그부터 정리한다.

필요할 경우 logrotate를 강제로 실행할 수 있다.

```bash
sudo logrotate -f /etc/logrotate.d/agent-app
```

### 중기 대응

로그 회전 설정을 조정한다.

예:

```text
size 5M
rotate 5
compress
```

로그 증가 속도가 빠른 경우 회전 크기나 보존 개수를 서비스 특성에 맞게 변경한다.

### 장기 대응

로그가 급증한 원인을 해결해야 한다.

* 동일 오류가 반복되는지 확인
* 애플리케이션 로그 레벨 확인
* 디스크 사용률 모니터링
* 일정 사용률 이상일 경우 알림 설정
* 중앙 로그 시스템 도입 검토

즉 로그 급증 시 대응은 다음 흐름으로 수행한다.

```text
로그 급증 감지
      ↓
디스크 사용량 확인
      ↓
오래된 로그 정리 / 강제 회전
      ↓
logrotate 정책 조정
      ↓
로그 급증 원인 분석 및 모니터링
```

단순히 로그를 삭제하는 것이 아니라 서비스 장애를 방지하면서 원인을 추적할 수 있도록 필요한 로그는 보존하는 것을 원칙으로 한다.
